# TabScore 성능 측정

배포 빌드를 Playwright Chromium에서 열고 1트랙×32마디, 8트랙×100마디, 20트랙×300마디를 같은 절차로 측정합니다.

```sh
pnpm test:perf
pnpm test:perf --grep '8 tracks'
```

각 입력의 브라우저 타임스탬프부터 입력 후 첫 애니메이션 프레임 직전까지를 50회 측정합니다. 같은 픽스처를 다시 열고 20회 편집 전후의 GC 이후 힙을 비교합니다. 재생이 시작된 뒤 4초 동안 50ms 초과 longtask를 셉니다. 파일 크기는 Ctrl+S로 받은 실제 네이티브 다운로드의 바이트 수입니다.

| 측정값 | 적용 전 | R8 통합 후 | SVG·편집 경로 최적화 후 | 재생 시간 표시 분리 후 | 목표 |
|---|---:|---:|---:|---:|---:|
| 편집 중앙값 / p95 | 223.4 / 347.1ms | 31.4 / 58.0ms | 11.8 / 27.3ms | 11.6 / 20.1ms | p95 < 50ms |
| 커서 중앙값 / p95 | 114.5 / 216.4ms | 5.4 / 20.3ms | 4.5 / 13.0ms | 8.0 / 16.3ms | p95 ≤ 16ms |
| 20회 편집 후 힙 증가 | 59,796,472B | −1,459,508B | −1,293,524B | −1,338,080B | ≤ 50MB |
| 4초 재생 longtask | 38회 | 3회 | 4회 | 1회 | ≤ 2회 |
| 네이티브 다운로드 | 1,748,157B | 206,914B | 206,914B | 206,914B | ≤ 1.5MB |
| 마운트된 SVG 요소 | 24,237 | 3,935 | 3,935 | 2,691 | 요소 수천 개 수준 |

적용 전 기준은 `8f0db0b`입니다. Linux x64, Node 24.22.3, Chromium 149.0.7827.0, 1280×768에서 측정했습니다. 결과 JSON은 테스트 첨부에 남습니다. CI에서 `TABSCORE_BASELINE_EDIT_P95`에 같은 러너에서 측정한 기준을 설정하면 20% 이상 증가할 때 경고합니다. 성능 목표를 놓친 결과도 첨부하고, 공용 CI의 변동을 감안해 경고로 남깁니다.

8트랙×100마디를 모든 열에서 사용했습니다. 첫 통합 빌드에 v6 저장·패치 이력, 오버레이, 레이아웃 캐시, 페이지 가상화와 재생 Worker를 적용했습니다. 다음 빌드는 변함없는 SVG 요소와 배치 좌표를 재사용하고 편집 시 붙임줄·검증 계산을 줄였습니다. 마지막 빌드는 재생 시간 구독을 도구줄의 시간 표시에 한정했습니다. 마지막 커서 p95는 목표보다 0.3ms 높았고 나머지 목표는 그 실행에서 통과했습니다. GC 이후 힙은 적용 후 측정에서 초기 측정값보다 낮았습니다.

최종 R8 빌드(`0594327`)를 같은 절차로 세 번 더 측정했습니다. 편집 p95는 19.9 / 22.1 / 19.6ms, 커서 p95는 13.7 / 15.1 / 16.5ms, 재생 중 longtask는 0 / 3 / 0회였습니다. 같은 빌드에서도 커서와 재생의 경계값은 실행마다 달랐습니다. 파일 크기와 SVG 요소 수는 세 번 모두 206,914B와 2,691개였습니다.
